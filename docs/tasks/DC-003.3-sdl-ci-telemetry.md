## Description

### Problem Statement
With `DC-003.1` and `DC-003.2` delivering the SDL backend lifecycle and swapchain surface support, the remaining gap for roadmap initiative `DC-003` is end-to-end validation and observability. Today our CI presets do not build or run SDL-focused suites, telemetry lacks SDL-specific counters, and documentation does not explain how contributors can diagnose SDL failures. Without this final leg, regressions on the SDL path will go undetected and downstream teams will not have actionable signals when SDL setup fails on developer machines or automation.

### Proposed Solution
Enable SDL-aware build and test presets in CI (Linux + Windows minimum) that compile platform/runtime tests and exercise SDL swapchain integration. Extend diagnostics/telemetry so backend selection, initialization failures, and event pump timings are captured with backend identifiers. Update documentation (platform README, SDL checklist, roadmap/task records) with the new validation steps, CI coverage, and telemetry fields. Coordinate with tooling to surface telemetry within the diagnostics viewer and ensure failure cases demote cleanly to the mock backend while reporting the precise reason.

### Success Criteria
- CI executes deterministic SDL unit + integration suites on at least one Linux and one Windows preset, failing fast on regressions.
- Telemetry includes SDL backend identifiers, initialization status, and per-frame event pump metrics consumable by diagnostics tooling.
- Documentation provides clear SDL setup, CI coverage, and troubleshooting guidance, closing the roadmap action item for `DC-003`.

## Test Plan

### Unit Tests
```cpp
TEST(SdlWindowBackend, EmitsTelemetryOnInitializationFailure) {
    ScopedSdlDisable guard;
    auto window = engine::platform::create_window(WindowConfig{
        .backend = WindowBackend::SDL,
    });
    ASSERT_FALSE(window);
    auto telemetry = collect_recent_window_telemetry();
    EXPECT_THAT(telemetry.backend, Eq("sdl"));
    EXPECT_THAT(telemetry.status, Eq(WindowInitStatus::FallbackMock));
}
```

## Implementation Notes

### Design Considerations
- Reuse existing telemetry schema categories (`runtime.platform.*`, `platform.window.*`) and extend with SDL-specific dimensions.
- Ensure CI presets install SDL packages via reusable scripts so additional pipelines can opt-in without duplication.
- Leverage existing diagnostics viewer parsing infrastructure; only add SDL-specific rendering and assertions.
- Keep telemetry optional at runtime (e.g., compile-time flag or minimal overhead) to avoid impacting production builds.

### Risks & Mitigations
| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| CI runners lack GPU/display capabilities for SDL | Medium | Medium | Use headless SDL hints and xvfb/wayland headless drivers; document fallback strategy. |
| Telemetry increases runtime overhead | Low | Medium | Sample timings sparsely and aggregate; validate overhead via performance tests. |
| Diagnostics viewer changes break existing telemetry parsing | Medium | Medium | Add regression tests covering both legacy GLFW and new SDL telemetry payloads. |
| Windows CI SDL setup drifts from developer workflow | Medium | Medium | Capture setup steps in scripts/ci docs and provide automated install script. |

### Alternative Approaches
1. **Rely solely on developer testing**: rejected—CI must guard SDL path to avoid regressions.
2. **Introduce separate telemetry pipeline**: rejected—reuses existing telemetry schema keeps instrumentation consistent across backends.
